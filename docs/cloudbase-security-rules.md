# CloudBase 数据库安全规则

## 当前状态：已采用 ADMINONLY，不是自定义规则

`rooms` 和 `players` 两个集合在 CloudBase 控制台里已经创建为
**ADMINONLY**（仅云函数的环境身份能读写，客户端 SDK 完全没有权限）。
这是已经落地的真实配置，不是本文档的建议，本次任务也不会去修改它。

这个选择绕开了本文档更早版本反复讨论的"要不要用自定义规则、能不能表达
跨集合成员检查"这些问题——客户端不管是 `get()`/`where()` 还是 `watch()`，
在 ADMINONLY 下都没有权限直接接触这两个集合，不需要靠规则语言去区分
"房间成员"和"非成员"。所有房间状态的读取都改为经过云函数的
`getRoomState` action，由服务端用可信 `uid` 做成员校验。完整的架构说明见
[docs/architecture.md](./architecture.md) 的"实时同步"章节，安全层面的
结论见 [docs/security.md](./security.md)。

## `game_events` 集合（预留，Milestone 1 不创建）

如果以后创建这个集合，建议同样配置为 ADMINONLY——这类事件日志不应该被
客户端直接读写，所有写入都应该由云函数在处理游戏逻辑时产生。

## 索引建议

- `rooms.roomCode`：建一个普通索引，`getRoomByCode` 会频繁按这个字段查询。
- `rooms.status` + `rooms.updatedAt`：如果以后要做"清理过期房间"的定时任务，
  按这两个字段的复合索引会更高效。Milestone 1 暂不需要。

## 历史记录：自定义规则方案的调研（已不采用，仅供参考）

在数据库创建为 ADMINONLY 之前，本文档讨论过"如果要用自定义安全规则允许
房间成员直接读 `rooms`，应该怎么写"这个问题。保留在这里，是因为调研过程
中核实的 CloudBase 规则语言真实语法（和本项目早期错误使用的 Firebase
风格语法的对比）仍然有参考价值，以后如果要给别的集合写自定义规则，
可以避免重复踩坑。

### 一个真实踩过的错误：套用了 Firebase 的规则语法

早期草稿写过 `resource.data`、`auth.uid == ...`、
`doc.players[*].playerId` 这类语法，这是**从 Firebase 规则语法套过来的，
不是 CloudBase 实际支持的语法**。核实后的真实情况：

- CloudBase 安全规则的变量名是 `doc`，不是 `resource.data`。
- 全局变量：`auth`（`auth.uid`/`auth.openid`/`auth.loginType`）、
  `doc`（文档数据或查询条件，取决于操作类型）、`now`、
  `request.data`（仅 create/update 时存在）。
- 跨集合查找用 `get()` 函数，格式必须是
  `` get(`database.集合名.文档id`) ``（反引号模板字符串），
  一个表达式最多 3 个 `get`、最多访问 10 个不同文档，嵌套深度最多 2。
- **不支持数组通配符**，没有找到 `doc.players[*].uid` 或
  `doc.players.some(p => p.uid == auth.uid)` 这类"检查数组里是否存在
  某个子字段等于某值"的语法。这正是"房间成员是一个数组"这种场景下
  自定义规则很难表达的根本原因——`rooms.players` 是多人数组，不是像
  `_openid` 那样的单一归属字段，标准的"改写成 `where` + `{uid}`/`{openid}`
  占位符"模式是为"一个文档只属于一个用户"设计的，不能直接套用。
- 按文档 ID 查询（`doc(id).get()`）如果规则里引用了 `doc`，系统会先真的
  读一次这份文档，再判断规则是否满足；但官方文档特别提醒：这类"仅指定
  `_id`"的操作大部分情况下**不满足安全规则的子集要求**，需要改写成
  `where()` 查询并用 `"{uid}"`/`"{openid}"` 占位符。
- `watch()`（实时推送）是否复用同一套 `read` 规则、是否支持跨集合
  `get()` 查找，官方文档没有专门说明——这个问题最终也没有必要解决，
  因为改用了 ADMINONLY + `getRoomState` 的方案，`watch()` 从一开始就不会
  被前端调用。

### 为什么"只要求 `auth.uid != null`"是不够的

更早的草稿还写过 `read: "auth.uid != null"` 这类规则，这完全不能防止
任意匿名用户枚举所有房间数据——它只检查了"请求方已登录"，没有检查
"请求方是不是这个房间的成员"。任何匿名登录的用户都能借此读到别人房间的
完整数据。这是必须指出的错误，即使最终没有走自定义规则这条路，也要记录
下来避免以后给别的集合写规则时重复这个错误。
